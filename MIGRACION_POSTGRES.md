# Migración a PostgreSQL — guía operativa (Bloque B)

`db.py` soporta **dos backends** y elige automáticamente según `DATABASE_URL`:

- **SQLite** (por defecto) — dev/tests, sin dependencias externas.
- **PostgreSQL** — producción, cuando `DATABASE_URL` empieza por `postgresql://`.

No hay que cambiar código de la app para alternar: es solo una variable de
entorno. `psycopg` únicamente se importa cuando el backend es Postgres.

## Cumplimiento de la tabla B2 del handoff

Se implementa la tabla B2 **completa** en el schema de PostgreSQL, manteniendo a
la vez SQLite operativo para dev/tests (el código Python lee ambos de forma
agnóstica).

| Tema | Handoff | PostgreSQL | SQLite | Cómo se hace agnóstico |
|------|---------|-----------|--------|------------------------|
| Placeholder `?` | `%s` | `%s` (shim) | `?` | `db.py` traduce `?`→`%s`; los callers no reescriben queries |
| Fechas | `TIMESTAMPTZ` | **TIMESTAMPTZ** | TEXT ISO | `as_naive_utc()` normaliza str/datetime al comparar; pool en UTC |
| Flags activo/used | `BOOLEAN` | **BOOLEAN** | INTEGER | Literales `TRUE`/`FALSE` en SQL (válidos en ambos); params `bool` |
| `attempts` | (contador) | INTEGER | INTEGER | Es un contador, no aplica BOOLEAN |
| `data` de listas | `JSONB` | **JSONB** | TEXT | `::jsonb` al insertar; `json.loads` solo si llega str |
| Upserts | `ON CONFLICT` | ON CONFLICT | ON CONFLICT / `INSERT OR REPLACE` | Compatible |
| IDs | `IDENTITY` | **GENERATED BY DEFAULT AS IDENTITY** | AUTOINCREMENT | `RETURNING id` (no `lastrowid`) |
| Búsqueda LIKE | `pg_trgm`+GIN | `pg_trgm`+GIN, `ILIKE` | `LIKE` | `ILIKE` en PG conserva el case-insensitive de SQLite |
| `_lock`/`_conn` | eliminar | pool (sin lock global) | conexión por llamada | — |
| Pool | obligatorio | `psycopg_pool` (lazy, UTC) | n/a | `VERIFYDATA_PG_POOL_*` |

> Único cambio de tipo NO nativo: las fechas en **SQLite** siguen como TEXT
> (SQLite es de tipado dinámico y no tiene `TIMESTAMPTZ` real); en **PostgreSQL**
> sí son `TIMESTAMPTZ`. `as_naive_utc()` unifica la comparación.

## Puesta en marcha

1. Provisiona Postgres (Coolify). Crea la BD `verifydata`.
2. Define en el entorno del servicio:
   ```
   DATABASE_URL=postgresql://user:pass@host:5432/verifydata
   VERIFYDATA_PG_POOL_MIN=2
   VERIFYDATA_PG_POOL_MAX=16        # ver dimensionamiento
   VERIFYDATA_PG_POOL_TIMEOUT=30
   ```
3. `pip install -r requirements.txt` (instala `psycopg[binary,pool]`).
4. Al arrancar, `init_db()` crea el schema + la extensión `pg_trgm` y el índice
   GIN. Si el rol de BD no puede `CREATE EXTENSION`, se avisa en el log y la
   búsqueda sigue funcionando (sin índice, más lenta): pídele al DBA que corra
   una vez `CREATE EXTENSION pg_trgm;`.
5. Migra los datos existentes (opcional, si vienes de SQLite):
   ```
   python3 migrate_sqlite_to_pg.py            # users
   python3 migrate_sqlite_to_pg.py --include-lists   # + listas (re-descargables)
   python3 migrate_sqlite_to_pg.py --dry-run  # solo contar
   ```
   Migra `users` (preservando id). Es
   idempotente. Usa psycopg parametrizado, así que **no** sufre los problemas de
   versiones de `pg_dump` ni el dollar-quoting de los hashes `$`.

## Dimensionamiento del pool (⚠️ crítico)

`runs.py` lanza **16-32 workers por búsqueda** que consultan la BD
(`search_entries`). Con varios usuarios simultáneos el pico de
operaciones concurrentes crece.

- Las operaciones de BD son **cortas** (una query y liberan la conexión): el pool
  las encola cuando se agota, no falla. Un `max` moderado (16) absorbe ráfagas.
- `max` **nunca** debe superar `max_connections` de Postgres (default 100),
  contando otras réplicas/servicios que compartan el server.
- **Regla de oro del código:** una operación de BD **no** debe anidar otra
  (`get_db` dentro de un `get_db` ya abierto). Si se retiene 1 conexión y se pide
  otra, con `N` hilos > `max` se produce deadlock por agotamiento del pool. El
  código actual no anida (verificado); mantenlo así.

## Checklist de verificación B5 (antes de dar por cerrado)

- [x] `init_db()` crea el schema en Postgres limpio sin errores. *(verificado E2E con PG 16)*
- [x] Tipos nativos correctos: `TIMESTAMPTZ`, `BOOLEAN`, `JSONB`, `IDENTITY`. *(verificado)*
- [x] Expiración de OTP y de sesión correctas con `TIMESTAMPTZ` (válido vs expirado). *(verificado)*
- [ ] Login OTP + SSO end-to-end con los `users` migrados. *(requiere SMTP/Entra reales)*
- [x] Upsert/búsqueda de listas (`ON CONFLICT`, `ILIKE`, índice trgm, JSONB→dict). *(verificado)*
- [x] Rate limit OTP persistente (tabla `otp_rate_limit`) limita tras N intentos. *(verificado)*
- [x] Auditoría persistente: cada evento queda en `audit_log` (JSONB). *(verificado)*
- [x] Migración de datos: `int→bool`, `texto→jsonb`, ids preservados, idempotente. *(verificado)*
- [x] **Prueba de carga del pool:** 400 tareas / 40 hilos / `max=10` sin timeouts. *(verificado en local; repetir en la infra real con búsquedas concurrentes reales antes de un evento)*

> Los ítems marcados se verificaron contra un PostgreSQL 16 local durante el
> desarrollo. El único pendiente (login OTP/SSO end-to-end) depende de
> infraestructura real (SMTP/Entra) y debe confirmarse en staging, junto con
> repetir la prueba de carga del pool en el Postgres de Coolify.

## A6 y A8 cerrados con Postgres

El handoff indicaba que A6 (rate limit) y A8 (auditoría) "se cierran del todo
cuando ya tengas Postgres". Hecho:

- **A6:** tabla `otp_rate_limit` — el rate limit de OTP (por IP y por email) es
  ahora persistente (sobrevive reinicios, se comparte entre workers), ya no en
  memoria.
- **A8:** tabla `audit_log` — cada evento de auditoría AML (búsqueda, login,
  descarga de PDF, cambios de RBAC, refresh de listas) se persiste con su
  detalle en `JSONB`, además del log estructurado. Retención configurable
  (`VERIFYDATA_AUDIT_RETENTION_DAYS`, 0 = nunca purgar, adecuado para SARLAFT).
  Los `print()` de diagnóstico del servicio (scrapers, solvers) se enrutan por
  `logging`.
